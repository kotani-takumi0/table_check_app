# App Store 申請の準備（Swift 版・録音なし）

この文書は、Swift 版（`apps/ios-swift`）を録音なしで App Store に出すための下書きです。説明文・プライバシーの回答・審査メモは、出したあとに店の人のことばで直してかまいません。

申請そのものは匠さんが行います。署名と App Store Connect へのアップロードは、匠さん自身の Mac の Xcode で行います。GitHub Actions は署名しません。このリポジトリを触る AI も、申請ボタンは押しません。

版を 3.0.0 にするのは、別の `chore/release-3.0.0` です。この文書を書いた時点の `MARKETING_VERSION` は 0.1.0 のままです。0.1.0 のまま Archive しないでください。

録音のコードを隠して入れ、あとから遠隔でオンにすることはしません。この申請版には録音を入れません。

店の名前・お客さんの記録・スタッフのメールは、説明文・スクショ・審査メモに書きません。下の例はすべて架空です。

## App Privacy（集めるデータの下書き）

2026-10-18 に Swift 版のコードを読んで書いた下書きです。Firebase Analytics と Crashlytics は入っていません。追跡（トラッキング）もしません。広告 ID も取りません。

App Store Connect のプライバシーの質問は、次のように答えます。目的はどれも「App の機能」。追跡には使いません。アカウント（メールと利用者 ID）に結び付きます。

| データの種類 | 集めるか | コード上の中身 |
|---|---|---|
| メールアドレス | 集める | ログインとアカウント作成で、Firebase Authentication にメールアドレスを送る（`AuthService.signIn` / `signUp`） |
| 利用者 ID | 集める | Firebase Authentication の uid。店のデータは `shops/{uid}/` に置く。ご意見の文書 ID と `shop` にも uid を書く |
| カスタマーサポート | 集める | お知らせの「ご意見を送る」。自由に書いた文（`message`、1000 字まで）を Firestore の `feedback` に書く。一緒にアプリの版（`version`）、`ios`（`platform`）、設定の店名（`shopName`）、ログインしている店の uid（`shop`）、送った時刻（`createdAt`）を書く。アプリから読み返すことはできない |
| その他のユーザーコンテンツ | 集める | 店の人が入れた営業のデータ。卓の状態・人数・コースと料理・案内や退店などの時刻・席の配置・店のタイマー・設定の店名。お客さんの氏名・電話番号・メールは持たない |
| 名前 | 集めない | 人の名前は持たない。設定の店名は店の表示名で、上の「その他のユーザーコンテンツ」とご意見の `shopName` に含める |
| 音声・マイク | 集めない | 録音のコードは無い。マイクの許可も出さない |
| 位置情報・連絡先・写真 | 集めない | 使っていない |
| クラッシュ・パフォーマンス | 集めない | Crashlytics は入っていない |
| 製品の操作（分析） | 集めない | Analytics は入っていない。記録に写す `platform`（`ios`）と `appVersion` は、その卓を最後に書いた端末の印で、利用状況の分析としては送っていない |

パスワードは、ログインとアカウント作成のときだけ Firebase Authentication に送ります。Firestore には書きません。Apple の質問票に「パスワード」の種類は無いので、上の表には列を作りません。メールアドレスの欄で、アカウントの認証に使う、と分かるようにします。

ご意見の自由文は、店の運営データとは別に「カスタマーサポート」として申告します。空のまま送ることはできません（空白だけは送れない）。審査員が送らなくても、アプリは使えます。

端末の中だけに残り、サーバーへは送らないもの（プライバシーの「収集」には入れない）:

- 音・ハプティクス・外観・通知のオンオフ（`UserDefaults`）
- お知らせを見たか、ご意見を送ってからどれだけ待つか
- サーバーとの時差の見積もり（測るための `clockProbes/{uid}` にはサーバー時刻だけを書く）
- ローカル通知（卓番と「ラストオーダーの時間です」などの文。プッシュ用のトークンは作らない）
- 設定の「記録」から書き出した CSV（共有シートで、使う人が自分で渡す。中身は上の営業のデータと同じ）

「ほかの端末がこの卓を開いている」印（`editing/{端末ID}`）の ID は、アプリを開くたびに作る乱数で、端末には保存しません。ハードウェアの識別子ではないので、「デバイス ID」としては申告しません。

同じ内容を、アプリのプライバシーマニフェスト（`Minopal/PrivacyInfo.xcprivacy`）にも書いてあります。

- メールアドレス・利用者 ID・カスタマーサポート・その他のユーザーコンテンツ。いずれも App の機能のため。追跡しない。利用者に結び付く
- 必須理由 API は `UserDefaults`（理由 `CA92.1`。このアプリだけが読む設定）
- マイクのデータ種類は書いていない

Firebase の SDK が自分のマニフェストを同梱します。コンソールの回答は、アプリのマニフェストと上の表がずれないようにします。

## 審査用アカウントと使い方

審査用のアカウントは、App Review のためだけに新しく作ったアカウントにします。営業している店のアカウントは使いません。中身は架空のテストデータだけにします（架空の店名、架空の人数、架空のコース名）。審査が終わったら、匠さんがパスワードを変えるか、アカウントを消します。同じパスワードのまま残しません。

資格情報はここに書きません。App Store Connect の「審査メモ」に、匠さんが自分で入れます。

```
審査用アカウント（この申請のためだけに作ったもの。営業している店のアカウントではない）:
メール: （審査用のメールアドレス）
パスワード: （審査用のパスワード）

このアカウントの店には、架空の店名と架空の卓だけが入っています。

1. アプリを開く
2. 上のメールとパスワードで「ログイン」を押す
3. 「ログインせずに使う」は押さない（申請ビルドでは、営業のデータがあるプロジェクトではこのボタンは押せない）
4. 配置図の空席を押すと案内、使用中の卓を押すと詳細が出る
5. 詳細の大きいボタンで、お通し・ラストオーダー・退店へ進める。もう一度押すと戻せる
6. 設定で、時間のルール・店のタイマー・この端末を見られる
7. お知らせの「ご意見を送る」は空のままでよい
8. 通知の許可を聞かれたら、許可しても断っても先へ進める
9. マイクの許可は出ない
```

審査用の店は、提出する前に席の配置を保存しておきます。保存前だと「最初のページ」が出ます。テンプレート「居酒屋・21卓（カウンターあり）」を選ぶか、空の配置から作り、店名は「架空食堂」のように明らかに架空の名前にします。コース名と料理名も架空のもの（例: 「テストコース」「架空の前菜」）に変えます。初期のコース一覧のままにしないでください。卓は 2 名や 4 名など、架空の人数を数組入れておきます。

署名と App Store Connect へのアップロードは、匠さん自身の Xcode で行います。CI のビルドは署名していないので、そのまま提出できません。

## スクリーンショット

本物の店名・本物のコース名・本物のメールは写しません。店名は「架空食堂」。人数・時刻・コースは作り物だけにします。パスワードは写しません。

撮る画面:

1. ログイン（メール欄は空、または `review@example.invalid` のような架空のアドレス。パスワード欄は空）

## TestFlight から申請まで

匠さんが、この順で行います。

1. 版を 3.0.0 にする PR（`chore/release-3.0.0`）がマージされてから Archive する。この PR では版を上げていない
2. Apple Developer で、App ID `jp.minopal.app` に App Attest を付ける。資格の値は production（`Minopal/Minopal.entitlements`）
3. Firebase コンソールで、この iOS アプリに App Check の App Attest を登録する。強制（enforcement）は Authentication も Firestore もオフのままにする（記録だけ）。Web 版も含めて全部のアプリが App Check に対応してから、断る設定に変える。このリポジトリの `firestore.rules` は変えていない
4. App Attest を使えない端末だけ DeviceCheck に戻す。強制がオフなので、DeviceCheck をコンソールに登録していなくても読み書きは断られない。登録するなら DeviceCheck も足す
5. デバッグトークンは DEBUG ビルドのログに SDK が出すことがある。リポジトリにも CI のシークレットにも置かない。コンソールへの登録は、手元の開発ビルドで必要になったときだけ匠さんが行う
6. `GoogleService-Info.plist` を手元の `Minopal/` に置く（リポジトリには入れない）。置かずに Archive するとエミュレータ向けの設定になる
7. 試し用のアカウントを、この試しのためだけに作る。中身は架空のデータだけにする。営業している店のアカウントではログインしない。店の iPhone・iPad に TestFlight で入れて、案内・詳細・設定・お知らせ・通知の許可（断っても使えること）を触る。マイクの許可が出ないことを確かめる。試しが終わったら、パスワードを変えるかアカウントを消す
8. 署名とアップロードは、匠さん自身の Xcode で行う。Product → Archive → Distribute App。CI の成果物は署名していない
9. 審査用アカウントを、審査のためだけに新しく作る。中身は架空のデータだけにする。営業のアカウントは審査メモに書かない。審査が終わったら、パスワードを変えるかアカウントを消す
10. 説明文、スクショ、1024 のアイコン（Archive から渡らないとき）、プライバシーポリシーの URL、上の App Privacy の回答、審査メモを入れてから申請する。申請ボタンは匠さんが押す
11. 輸出コンプライアンスを聞かれたら、このアプリが使う暗号は Firebase への HTTPS（標準的な暗号化）だけ、と答える。独自の暗号は足していない

## 録音が入っていないことの確認

`npm run ios-swift:check-recording`（`apps/ios-swift/scripts/check-no-recording.mjs`）が、次を見つけると失敗します。

- Info.plist・entitlements・プライバシーマニフェストの `NSMicrophoneUsageDescription`
- それらの `UIBackgroundModes` に `audio` がある
- `project.yml` が同じキーを足している（行コメントは見ない）
- Swift が `AVAudioRecorder`、`AVAudioEngine` の入力、`requestRecordPermission`、`import AVFoundation` などの録音 API を使っている

システムの通知音（`AudioToolbox`）は録音ではないので、失敗にしません。

PR の CI は、ソースの確認に加えて、署名しない Release ビルドの `Minopal.app/Info.plist` も見ます。
